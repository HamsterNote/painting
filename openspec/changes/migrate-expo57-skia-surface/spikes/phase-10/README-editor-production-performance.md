# Phase 10 Editor Production Performance

`scripts/perf/editor-production-performance.mjs` is a Web-only production measurement runner owned for verification by the parent orchestrator. It first runs exactly:

```sh
pnpm run prepare:playground-artifacts && pnpm --filter @hamster-note/painting-playground build
```

After that export completes, it starts a fresh local server for `apps/playground/dist` and opens the production root `/?perf=1`. The server implementation is `scripts/perf/static-spa-server.mjs`: actual extension-bearing JavaScript, CSS, WASM, font, image, map, and other asset requests map only to their files and return `404` if missing. Only extensionless route paths can fall back to `index.html`. Its MIME map includes `.wasm -> application/wasm`, `.js/.mjs -> text/javascript`, `.css -> text/css`, and common font and image formats; the exact map is recorded in the JSON artifact.

The runner uses headless Playwright Chromium at `1440x900`, device scale factors `1` and `2`, and five independent browser contexts per scale factor. Each context must establish all production prerequisites before any input measurement: the performance diagnostics DOM reports `workload-ready=true`, `workload-strokes=100000`, and `frame-ready=true`; the API snapshot confirms performance mode and exactly 100,000 V2 strokes; and same-origin `/canvaskit.wasm` responds `200` with `application/wasm`. A prerequisite failure is retained as a failed context; it is not retried to manufacture a passing sample.

For each valid context the runner records the raw readiness snapshot and `runRebaseProbe()` result, requiring positive and negative approximately `1e9` coordinates at scales `.25`, `1`, and `8`, with finite frame state. It resets diagnostics and calls only `runHighRatePenInput({ eventsPerSecond: 120, durationMs: 10000 })`, which dispatches synthetic `PointerEvent`s through the production host adapter. Before the first dispatch, the page creates all 1,200 absolute 120 Hz deadlines for the 10-second workload. Every deadline has an independently registered timer; the next event is never registered from the preceding `dispatchEvent` return. Each callback dispatches its event even when the main thread is late, recording `scheduledAt`, `callbackAt`, `backlogAtCallback`, immutable unique `eventId`, monotonic `sequence`, `emittedAt`, pointer, and phase. The capture listener carries the exact identity to adapter receipt, which may consume it only while pending pointer, phase, and sequence agree. The resulting raw sample also records `receivedAt`, React `commitAt`, `nextFrameAt`, and their latencies. The next rAF is settled only after receipt and only when `nextFrameAt >= receivedAt >= emittedAt`; a callback that shares the receipt's frame but has an earlier rAF timestamp waits for the following frame instead of creating a false negative latency.

The measurement window starts immediately before formal dispatch one. It ends only after event 1,200's receipt, its associated React commit, and the required next rAF are all settled, or when the bounded settlement deadline expires. At that point the page finalizes missing records as invalid, stops both rAF and long-task observation, and only then returns one raw measurement collection to Playwright. Snapshot serialization and Playwright object transfer are therefore outside the observed rAF/long-task window. Long-task records contain `startTime`, `duration`, and associated event/commit identities.

Every pointer record remains in the raw artifact. Missing or mismatched event identity, pointer/phase/sequence mismatch, missing deadline/callback/receipt/commit/frame, a negative latency, or any clock/order violation receives an explicit `invalidReason`. These records are not deleted, filtered to zero, or included in p50/p95/max. The runner reads the real schema at `results['1'].rounds` and `results['2'].rounds`, retaining per-round validity, invalid reason counts, ordering/negative counts, deadline span, actual open-loop span, lateness/backlog, metrics, and raw data. Each round independently requires all 1,200 ordered valid events, valid open-loop 10-second prerequisites, commit and event-to-frame metrics, rAF, long-task, and correctness/rebase checks. Any invalid record or workload prerequisite failure is `NO-GO`, even if an aggregate percentile looks acceptable.

`editor-production-performance.json` retains the old failed artifact under `historicalNoGoArtifact` and labels it through `runLineage` as `prior invalid measurement / clock association failure`; it is not deleted or promoted to a baseline. That old self-paced lineage took roughly 78-148 seconds for nominal 1,200-event runs and contained 5,988 negative event-to-next-frame samples at each dSF aggregate because its sampler paired a later pointer receipt with the earlier timestamp of the same rAF frame. The revised runner's `PASS` can establish an initial same-machine baseline; any `NO-GO` result cannot establish or replace a baseline.

The frozen contract is unchanged: p95 event-to-next-frame and available commit latency no more than `50ms`; rAF p95 no more than `33.4ms`; no long task over `100ms`; and prerequisites plus rebase correctness must pass. A negative event-to-next-frame sample is recorded raw but is an invalid latency signal and fails its check rather than being misrepresented as fast. A missing commit sample is an explicit contract gap and fails rather than being ignored. A browser without supported long-task data also fails rather than silently treating it as zero. `<=20%` degradation comparison remains pending until a valid frozen same-machine result exists. Corrected event/frame association validates the measurement, not the product performance: if a valid p95, long task, schedule prerequisite, or correctness check fails, the result remains `NO-GO`.

These results are intentionally limited. Chromium rAF is a main-thread scheduling signal, not GPU timing, pixel rendering evidence, or actual device frame rate. Synthetic `PointerEvent` input uses the formal adapter but is not hardware pen, touch, or mouse input. The result is not native Skia, iOS, Android, cross-device validation, or a product SLA. A passing report does not mark any OpenSpec task complete and does not claim the full change is complete.
